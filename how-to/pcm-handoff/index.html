Prepare ReEDS results for a PCM handoff

Choose and verify the source-system modifications needed before handing ReEDS results to a production-cost-model translator. This guide covers all eight registered r2x.transforms in current main and the published r2x-reeds 0.9.3 package. It does not treat eight successful plugin calls as proof of a valid PCM.

The ReEDS model produces the capacity-expansion runs consumed here. r2x-reeds parses those results and applies optional system modifiers; it does not solve the ReEDS model.

Start with the pip-based Pacific tutorial or your own completed ReEDS run. Keep original inputs and a parser-only checkpoint for comparison. Install r2x-cli, then install the published parser into its managed environment:

For a plugin’s current config help, use its entry-point name, for example:

Python virtual environments and the CLI runtime are separate. Record the package versions, solve/weather years, selected pipeline and input/policy file revisions with the saved output. The examples below use one solve year and one weather year.

The Python module prefix is r2x_reeds.. See registered entry points and public fields/source links. All eight config models allow omitted file paths, but several plugins then return success without changing anything. Operational input requirements below are stricter than model-construction requirements. Check effects, not just exit status.

Choose a sequence and avoid double counting

Section titled “Choose a sequence and avoid double counting”
flowchart TD
  P["Parse a working run copy"] --> D["PCM defaults<br/>review operating coefficients"]
  D --> B["Split generators<br/>inspect final unit capacities"]
  B --> I["Optional Canadian imports"]
  I --> Q{"Demand representation"}
  Q --> H["Modern purchaser load<br/>hydrogen and/or data-center components"]
  Q --> L["Legacy electrolyzer load<br/>alternative hydrogen representation"]
  H --> S["Optional optimal-siting increments<br/>do not repeat the same data-center load"]
  L --> C["Optional CCS incentive"]
  S --> C
  C --> E["Optional emission cap"]
  E --> V["Inspect, serialize and record provenance"]
  V --> T["Separate target translator and exporter"]

This is a defensible preparation order, not a universal requirement. Apply capacity-dependent defaults before splitting when following this recipe. Apply incentives and constraints after the fleet representation is settled. Existing electric demand profiles must be present before optimal siting.

Choose one representation for the same hydrogen load: the modern purchaser modifier or the legacy electrolyzer modifier. Likewise, do not feed the same loadsite_op increments to both purchaser-load data-center creation and optimal siting unless you have explicitly separated which demand each represents. Neither pair is a general deduplication mechanism.

1. Add operating defaults without rescaling startup coefficients

Section titled “1. Add operating defaults without rescaling startup coefficients”

add-pcm-defaults accepts pcm_defaults_dict or pcm_defaults_fpath; the inline dictionary takes precedence. Lookup tries generator name, then technology, then category. pcm_defaults_override=False fills only missing/null fields; True intentionally replaces existing values. Unknown model fields are not applied, and an unmatched generator can be skipped.

For the runnable base profile below, create policy/pcm-defaults.json:

The coefficient 50 dollars/MW is an illustrative policy input, not a recommended calibration. The base example explicitly overrides only this field to make its effect inspectable. For production use reviewed defaults and normally start with override disabled.

startup_cost remains $/MW through defaults and generator splitting. Do not multiply it by the original aggregated capacity. A downstream exporter converts the coefficient using the final unit capacity; applying that conversion twice would inflate startup costs. For example, a final 100 MW unit with a 50 $/MW coefficient corresponds to a 5,000-dollar startup charge, converted once by the appropriate target layer. Current splitting preserves the coefficient on each new unit. ramp_rate defaults are treated differently by this implementation: PCM defaults multiplies them by capacity. Inspect its output and target-unit contract rather than assuming every numeric default follows startup-cost behavior.

Check: select matched thermal units and compare startup_cost before/after; then check the coefficient remains 50 after splitting. Review unmatched/missing fields explicitly. Re-running override-enabled defaults is not a universal idempotence guarantee for capacity-scaled fields.

2. Disaggregate generator blocks

Section titled “2. Disaggregate generator blocks”

break-gens uses packaged reference sizes when reference_units=None; override with a JSON path or mapping. break_category="category" chooses the matching field. drop_capacity_threshold=5 discards remainders at or below 5 MW. Set an explicit threshold and reconcile any removed MW rather than expecting exact capacity conservation with that option enabled.

skip_categories, include_regions, include_generators and include_technologies restrict eligible units. Multiple include filters use OR, not AND. This modifier mutates the system and copies relationships, time-series associations and operating fields to split units.

Check: record generator counts and total MW before/after, inspect selected unit capacities and startup coefficients, and account for discarded remainders. The Pacific baseline with the package’s reference sizes has 292 generators before splitting and 673 afterward; counts are not a validation rule for other cases.

3. Add Canadian import energy budgets when applicable

Section titled “3. Add Canadian import energy budgets when applicable”

add-imports needs weather_year, canada_imports_fpath, canada_szn_frac_fpath and hour_map_fpath. Wide import files also need solve_year and a column named for that year. Inputs must supply regional annual imports, seasonal fractions and a chronological season mapping. The reader supports known source aliases such as *szn/frac_weighted and *timestamp/actual_period; compare your schema with the source before use.

It attaches daily hydro_budget in GWh, not hourly import power in MW. Daily fractions are normalized, and the annual input is divided by 1000 when constructing those GWh budgets. Check that the annual input is in the corresponding MWh basis. solve_year is retained as a time-series selection feature when supplied.

The parser excludes can-imports by default. Before choosing an imports profile, retain the other current exclusions but allow imports:

This replaces the exclusion list; it is not an append operation. The modifier cannot attach budgets to import generators that were never parsed.

Check: inspect matched import generators, list their hydro_budget series, confirm daily resolution and reconcile summed GWh with annual MWh divided by 1000. Supply matching series-selection features when querying them. Verify the season map covers the intended year; a successful no-op is not an import schedule.

4. Choose modern purchaser demand

Section titled “4. Choose modern purchaser demand”

add-purchaser-load requires hour_map_myr_fpath to do useful work. weather_year defaults to 2012; select solve_year when inputs contain several years. Supply only the applicable optional data:

  • hydrogen_production_capacity_fpath: cap data for electrolyzer, SMR or SMR-CCS components.
  • consume_characteristics_fpath: electricity-efficiency characteristics used by those consumers.
  • hydrogen_production_load_fpath: representative-period production load.
  • hydrogen_production_annual_load_fpath: optional annual targets used to scale production profiles.
  • loadsite_op_fpath: data-center demand by representative period.

The reader supports these CSV inputs and named groups in ReEDS output HDF5 files; see the dedicated purchaser-load guide. It creates ReEDSElectrolyzerDemand, ReEDSSteamMethaneReformingDemand and/or ReEDSDataCenterDemand and attaches max_active_power profiles. Existing demand components can suppress capacity-based duplicate creation; that does not make all repeated profile application safe.

Check: compare component names, counts, hourly MW and annual profile sums with the selected source technology, region and year. Verify scaling against annual targets where supplied. The pcm-hydrogen profile below omits loadsite_op_fpath so a separate siting profile cannot add the same data-center demand twice.

5. Or choose the legacy electrolyzer representation

Section titled “5. Or choose the legacy electrolyzer representation”

add-electrolyzer-load is the alternative for legacy fixed-load inputs. It needs weather_year and hour_map_fpath; provide electrolyzer_load_fpath and/or h2_fuel_price_fpath for the effects you want. Normalized load columns are region,hour,load_MW; hydrogen prices use region,month,h2_price. The hour map must join on hour. Do not point this at an arbitrary raw prod_load.csv and assume purchaser-load normalization applies.

It creates ReEDSDemand named <region>_electrolyzer with a fixed_load series; loads below 1 MW are skipped. Hydrogen price input affects matching hydrogen-fuel generators. The Python function is historically spelled add_electrolizer_load; the CLI name remains add-electrolyzer-load.

Check: inspect the new fixed-load profiles, weather-year timestamps and hydrogen-fuel prices. Use pcm-legacy instead of the modern purchaser profile for the same demand, not in addition to it.

6. Add cost-optimal siting increments to existing electric load

Section titled “6. Add cost-optimal siting increments to existing electric load”

add-optimal-siting needs loadsite_op_fpath and hour_map_myr_fpath. Select solve_year when filtering a multi-year file; the config also accepts a list and selects its first year. Source aliases such as r,allh,t,Value are normalized before representative periods expand into sequential hours.

The modifier adds increments to existing ReEDSDemand profiles. It does not create a demand profile when none exists. In pcm-sited, purchaser demand contains hydrogen only; the site increments therefore are not also represented by purchaser-created data-center components.

Check: snapshot the original electric-load series and compare the hourly difference and annual sum with the chosen loadsite increments. Confirm that unselected regions/years did not change and that profiles retain compatible length, timestamp and resolution.

7. Apply CCS credit economics to eligible units

Section titled “7. Apply CCS credit economics to eligible units”

add-ccs-credit needs all three paths: co2_incentive_fpath, emission_capture_rate_fpath and upgrade_link_fpath. Use normalized columns tech,region,vintage,incentive, tech,region,vintage,capture_rate, and from,to,region,vintage, respectively. Resolve any multi-year selection before supplying these inputs. Unknown or unmatched technologies can remain unchanged.

The modifier writes generator.ext["UoS Charge"] as negative $/MWh, computed from incentive $/ton times capture rate ton/MWh. This is a credit, not a startup cost or a one-time dollars-per-unit value. Keep the ton convention consistent.

Check: inspect the affected units’ UoS Charge and manually recompute at least one row. Confirm that your downstream translator/exporter carries this metadata into the intended target property; preserving an ext value alone does not prove that the PCM consumes it.

8. Record annual emission policy

Section titled “8. Record annual emission policy”

add-emission-cap needs existing CO2 supplemental attributes and either an explicit emission_cap or a compatible co2_cap_fpath. The file reader expects a single value cell. A raw multi-year ReEDS co2_cap.csv with *t,tonne_per_year is not that normalized shape; select the intended year and supply its value explicitly or prepare a one-row input.

default_unit="tonne" is the default. switches_fpath and emission_rates_fpath optionally enable precombustion additions; those inputs must match the helper’s expected switch and generator/emission/rate schemas. Do not blindly pass an unnormalized raw emissions report.

The stored constraint uses a metric scalar of 1000. Changing a unit label is not a general unit conversion. Inspect the constraint metadata and confirm its translation to the target emission policy before a PCM solve. Some system versions store this metadata in ext, others through a legacy fallback; do not assume all target exporters automatically consume it.

Check: verify a CO2 attribute exists, inspect the selected cap/year/units and manually reconcile the target cap and emission-rate basis. An absent cap or CO2 attribute can produce a successful no-op. The fixture’s raw cap file is not used as a normalized one-row policy file in the example below.

Inspect before handing off

Section titled “Inspect before handing off”

Save this as inspect_pcm.py. The CLI supplies the loaded system as sys:

For the baseline fixture, expect 673 generators and gas-cc startup coefficients: [50.0]. Record total MW and inspect load lengths/timestamps. The coefficient is still $/MW on the final units. Your own policy inputs should replace these fixture-specific assertions. Use saved-system inspection for direct Infrasys loading and profile values.

The prepared artifact still contains ReEDS components. Handoff to r2x-reeds-to-plexos plus r2x-plexos, or the Sienna translation workflow with r2x-sienna, as appropriate. Verify target properties, costs, emissions and profile units at that boundary. A serialized source system is a review checkpoint, not a native PCM export. Verify policy metadata after reload as well: do not assume a legacy dynamic constraint attribute survives every serializer; retain the selected policy input and pass it explicitly to the target workflow when required.

Tested coverage and limits

Section titled “Tested coverage and limits”

The published-package Pacific parse/modifier/reload tutorial, pcm-base, its startup-coefficient inspection, and CLI artifact loading were executed. The repository’s focused tests exercise all eight modifiers with purpose-built data, including startup-cost preservation. They are distinct from an all-modifier production run. Imports, purchaser/legacy demand, optimal siting, CCS and emission policy profiles above were not run against a complete external production case; their schemas, optional behavior and units were checked against current public configs and source. Supply and validate the needed inputs before claiming a PCM-ready handoff. For failures, use troubleshooting.
